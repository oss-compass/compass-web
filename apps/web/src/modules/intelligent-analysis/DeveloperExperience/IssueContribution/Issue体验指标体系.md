# Issue 体验指标体系

---

## 1. 概述

### 1.1 目标与适用范围

本体系用于评价：**外部开发者提交 Issue 后，是否获得及时响应、正确分流、持续推进、合理关闭和可复用结果**。

评分对象分为两个层级：

- **单条 Issue**：输出总分、阶段分、问题标签与严重问题标记。
- **周度报告**：聚合本周纳入样本的 Issue，输出报告总分、阶段分、质量分、效率分、主要问题与行动建议。

本体系**不直接评价** PR、Review、CI 或合并体验；与 Issue 解决直接相关的 PR、Commit、文档、版本发布，可以作为讨论推进和关闭决策的客观证据。

### 1.2 设计原则

1. **四阶段主流程**：围绕 I0 创建、I1 首响与分配、I2 推进讨论、I3 产出与闭环构建指标体系。
2. **质量/效率双轴**：同时评价“做得对不对”和“做得快不快”。
3. **每个指标只回答一个问题**：避免多个维度混在一个指标里，减少重叠评分。
4. **客观优先**：能由时间、事件、状态直接计算的，不交给 LLM 自由裁量。
5. **LLM 只做事实识别和质量分档**：识别实质回应、结论性评论、关闭原因等语义事实；最终分数仍按固定规则计算。
6. **不适用不计零分**：尚未进入某阶段或确实不适用的指标，不进入分母。
7. **严重问题封顶**：关键体验失败不能被其他高分抵消。

### 1.3 体系结构

| 阶段     | 名称       | 质量指标 | 效率指标 | 小计   | 报告权重 |
| -------- | ---------- | -------- | -------- | ------ | -------- |
| I0       | 创建       | 2        | 0        | 2      | 15%      |
| I1       | 首响与分配 | 2        | 2        | 4      | 20%      |
| I2       | 推进讨论   | 1        | 1        | 2      | 35%      |
| I3       | 产出与闭环 | 2        | 1        | 3      | 30%      |
| **合计** |            | **7**    | **4**    | **11** | **100%** |

> 正式指标体系共 11 项，采用“四阶段 + 双轴”结构。原 G 阶段不再纳入常规总分，Bot 治理作为专项分析单独呈现。

### 1.4 统一评分档位

| 分数 | 含义                                       |
| ---- | ------------------------------------------ |
| 100  | 完整实现该指标目标，没有明显缺陷           |
| 80   | 整体良好，仅存在轻微问题                   |
| 60   | 基本合格，但存在明显体验成本               |
| 40   | 只完成部分目标，主要缺口仍然存在           |
| 20   | 基本失败，但存在少量相关行为               |
| 0    | 达到评价条件后行为缺失，或存在明确相反事实 |

## 2. 统计口径

### 2.1 周报纳入范围

周报按“**所有 open Issue + 当周关闭 Issue**”的原则纳入样本。首版基线建议从 **2026-08-01（含）** 开始执行，后续可由 `baseline_start_date` 配置化。

纳入范围包括：

- **当周新建**的 Issue；
- **基线日之后创建且当前仍为 open** 的 Issue；
- **当周关闭** 的 Issue；
- **当周发生 reopened** 的 Issue。

核心目的不是只看“本周新建”，而是持续暴露“仍未解决、仍在处理中、刚刚关闭、跨周改进/回退”的真实体验状态。

### 2.2 生命周期分类

| 生命周期类型    | 定义                     | 本周评估方式                                    | 说明                       |
| --------------- | ------------------------ | ----------------------------------------------- | -------------------------- |
| 本周新建-已关闭 | 当周创建且当周关闭       | I0-I3                                           | 完整闭环样本               |
| 本周新建-进行中 | 当周创建、当前仍 open    | I0；I1/I2 按实际进展评估                        | 评估到当前阶段             |
| 历史-已关闭     | 非当周创建、当周关闭     | I0-I3 全阶段重评                                | 用于跨周对比与复测         |
| 历史-进行中     | 非当周创建、当前仍 open  | 有新活动时按 I0-I2 重评；无新活动时持续暴露卡点 | 反映跨周续程体验           |
| 重开            | 当周发生 closed→reopened | I0-I2 重评；如当周再次关闭则纳入 I3             | 表示上次关闭未真正完成闭环 |

### 2.3 排除规则

以下样本不纳入正式体验评分：

- **内部 Issue**：当前工程实现以“`Issue 创建者 == assignee`”作为硬排除规则；

### 3.2 质量与效率双轴

- **效率类（4 项）**：`obj-response-speed`、`obj-first-substantive-response-time`、`obj-progression-stall-degree`、`obj-closure-timeliness`
- **质量类（7 项）**：`sub-issue-type-correctness`、`sub-input-quality`、`sub-first-response-quality`、`sub-triage-owner-clarity`、`sub-discussion-progression`、`sub-closure-decision-correctness`、`sub-closure-reuse-value`

解释上：

- **效率轴**回答“处理是否及时、节奏是否连贯”；
- **质量轴**回答“处理是否正确、充分、可复用”。

| 阶段          | 报告权重 | 阶段内指标权重                                                                     |
| ------------- | -------- | ---------------------------------------------------------------------------------- |
| I0 创建       | 15%      | 分类正确性 0.50，输入质量 0.50                                                     |
| I1 首响与分配 | 20%      | 责任分配速度 0.25，首次实质回应时效 0.25，首响回复质量 0.25，分流与责任明确度 0.25 |
| I2 推进讨论   | 35%      | 讨论推进质量 0.50，讨论推进效率 0.50                                               |

权重设计原则：

- I0 没有单独效率轴，2 个质量指标等权；
- I1 四项指标等权，体现“接住问题”的完整性；
- I2 权重最高，体现推进讨论是体验主体；
- I3 同时覆盖关闭质量与关闭时效，强调闭环和知识沉淀。

## 4. 报告总分和阶段分计算

### 4.1 单条 Issue 指标分与阶段分

单项指标分统一落在 `{100, 80, 60, 40, 20, 0}` 六档中。

阶段分计算方式：

```text
stage_score
= Σ（指标分 × 阶段内指标权重）
÷ Σ（适用指标权重）
```

说明：

- 只对**适用指标**求和；
- not applicable 不计 0 分，也不进入分母；
- 如果某阶段无任何适用指标，则该阶段不输出分数。

### 4.2 单条 Issue 总分

先计算原始总分：

```text
raw_issue_score
= Σ（阶段分 × 阶段权重）
÷ Σ（有有效阶段分的阶段权重）
```

再应用严重问题控制：

```text
issue_final_score = min(raw_issue_score, score_cap)
```

### 4.3 严重问题封顶

| 级别         | 封顶分 | 触发条件示例                                                     |
| ------------ | ------ | ---------------------------------------------------------------- |
| 一级严重     | ≤39    | 攻击/羞辱用户、恶意误导、明知无效仍宣称解决                      |
| 二级严重     | ≤59    | 超过 14 天无任何社区响应、无解释关闭、用户明确表示未解决后仍关闭 |
| 三级重大风险 | ≤79    | 超过 30 天无实质推进、多次可避免用户催促、严重承诺违约           |

规则：

- 严重问题**只限制最高分**，不重复固定扣分；
- 封顶在 **Issue 层** 执行，之后再参与周报聚合；
- 严重问题要在报告中显式标注，不能只体现在最终分里。

### 4.4 周报阶段分、总分、质量分、效率分

先计算每个指标在报告期内的仓库指标分：

```text
repository_metric_score
= Σ（该指标在各 Issue 上的有效得分）
÷ 该指标成功评分的 Issue 数
```

再计算每个阶段的报告阶段分：

```text
report_stage_score
= Σ（该阶段在各 Issue 上的有效阶段分）
÷ 该阶段成功评分的 Issue 数
```

报告总分：

```text
report_total_score
= Σ（report_stage_score × 阶段权重）
÷ Σ（本周存在有效样本的阶段权重）
```

质量分：

```text
report_quality_score
= Σ（质量类 repository_metric_score × 指标权重）
÷ Σ（本周存在有效样本的质量类指标权重）
```

效率分：

```text
report_efficiency_score
= Σ（效率类 repository_metric_score × 指标权重）
÷ Σ（本周存在有效样本的效率类指标权重）
```

报告层建议同时输出：

- `eligible_n`：满足口径的 Issue 数；
- `scored_n`：成功评分的 Issue 数；
- `not_applicable_n`：某阶段 / 某指标不适用的样本数；
- `low_score_n`：低于 60 分的 Issue 数；
- `severe_issue_n`：触发严重问题控制的 Issue 数。

### 4.5 报告总分等级（2026-08-20 新增）

报告总分映射等级，与使用体验（SDX）、CI 体验采用同一档位（评估框架 v2.9 三场景等级统一裁定，2026-08-20）：

| 等级  | 分数范围 |
| ----- | -------- |
| **A** | 90 — 100 |
| **B** | 75 — 89  |
| **C** | 60 — 74  |
| **D** | 40 — 59  |
| **F** | 0 — 39   |

- 等级仅作用于**报告总分**；质量分、效率分、阶段分可选用同档呈现。
- 单条 Issue 分仍按六档指标分与严重问题封顶机制，不映射等级。

## 5. 跨周对比与复测（在业务系统中实现）

### 5.1 基本原则

跨周对比与复测能力由**业务系统**负责实现，不依赖报告人工整理。业务系统在每周报告生成后持久化快照，并在下周生成报告时自动完成历史匹配、分数对比和变化回填。

跨周对比以“**同一 Issue、同一指标、同一阶段**”为最小比较单元。每周报告生成后，系统保留以下快照：

- Issue 总分；
- I0-I3 阶段分；
- 11 项指标分；
- 严重问题级别；
- 主要问题摘要。

下一周生成报告时，自动拉取上周同一 Issue 的历史快照，形成复测结果。

### 5.2 复测状态定义

| 状态 | 判定规则                                |
| ---- | --------------------------------------- |
| 新评 | 上周没有同一 Issue / 同一指标的有效分数 |
| 改进 | 本周分 > 上周分                         |
| 回退 | 本周分 < 上周分                         |
| 持平 | 本周分 = 上周分                         |

### 5.3 输出方式

Issue 级明细建议直接展示：

| Issue | 阶段 / 指标           | 本周分 | 上周分 | 变化 |
| ----- | --------------------- | ------ | ------ | ---- |
| #161  | I3 / 关闭复用价值     | 0      | —      | 新评 |
| #158  | I1 / 首次实质回应时效 | 60     | 60     | 持平 |
| #149  | I2 / 讨论推进效率     | 80     | 60     | 改进 |

报告级也应支持以下对比：

- 报告总分：本周 vs 上周；
- 质量分 / 效率分：本周 vs 上周；
- I0-I3 阶段分：本周 vs 上周；
- Top 问题：新增、消失、持续存在、回退。

### 5.4 复测使用原则

- **有新活动才重评**：避免没有新证据却重复打分。
- **已关闭样本也允许复测**：尤其是 reopened 或关闭说明补充后。
- **同一 Issue 可连续多周出现在报告中**：目的是追踪改进，不是只做一次性结论。

## 6. Issue 分类与差异化评分规则

### 6.1 适用的 Issue 类型

本节直接按当前报告使用的 7 类 Issue 类型展开评分规则：

- 里程碑
- 漏洞
- 缺陷（Bug-Report）
- 需求（Requirement / Feature）
- 文档（Documentation）
- 咨询（Question）
- 任务（Task）

### 6.2 特别说明

- **里程碑**：首版先沿用“任务（Task）”的评分规则，重点看目标是否清楚、推进是否透明、闭环是否完整；
- **漏洞**：沿用更严格的时效与闭环要求，整体标准高于普通缺陷；
- **无法识别类型**：默认按“任务（Task）”处理；
- 全部指标统一按 **100 / 80 / 60 / 40 / 20 / 0** 六档计算。

### 6.3 六档评分含义

| 分值 | 含义 | 判定说明                                                                       |
| ---- | ---- | ------------------------------------------------------------------------------ |
| 100  | 优秀 | 关键证据齐全、结果明确、完成度高，几乎无明显体验损耗                           |
| 80   | 良好 | 整体达标且效果较好，但仍存在轻微缺口，不影响主要结论                           |

## 7. 报告呈现层

### 7.1 报告结构

建议周报采用以下结构：

```text
# Issue 贡献体验周报 · {project}

## 1. 执行摘要
- 报告总分 / 质量分 / 效率分
- 本周样本数（新建、历史进行中、历史关闭、重开）
- 主要短板与优先级

## 2. 本周关键数据
- 样本分布
- 各类型 Issue 数量
- 严重问题数量与占比

## 3. 体验路径总览
- I0-I3 阶段分
- 各阶段与上周对比
- 质量/效率双轴概览

## 4. Issue 得分与主要问题
- 每条 Issue 一行：总分、I0-I3、优先级、主要问题、上周分、变化

## 5. 主要问题（报告级）
- 从全部 Issue 中提炼共性问题、系统性问题
- 关联具体 Issue ID，但不逐条重复明细

## 6. 本周行动清单
- 行动建议、优先级、责任建议、关联 Issue ID
```

### 7.3 呈现原则

1. **一条 Issue 一行**：方便领导和维护者快速扫描全量状态。
2. **问题要可追溯**：每个问题都能回到具体 Issue、阶段和指标。
3. **共性问题上收**：第 5 节只写报告级共性问题，不重复第 4 节逐条问题。
4. **跨周变化前置展示**：本周分、上周分、变化必须进入摘要和明细主表。
5. **严重问题显式高亮**：不能只依赖分数体现，必须打标签。
6. **质量/效率同时可见**：避免只看总分，看不见问题到底出在“慢”还是“错”。

## 8. 执行结论

这套《Issue 体验指标体系》将原“报告升级方案”中的核心设计收敛为一套正式评分口径，重点解决以下问题：

- 从“只看本周新建”升级为“持续跟踪 open 与本周关闭样本”；
- 从分散指标升级为“四阶段 + 双轴 + 11 项指标”的统一口径；
- 从单周静态报告升级为“可复测、可对比、可追踪改进”的周报体系；
- 从统一一把尺子升级为“按 Issue 类型差异化解释时效与关闭合理性”；
- 从分散呈现升级为“摘要层、阶段层、Issue 层、共性问题层、行动层”五级联动的报告结构。
