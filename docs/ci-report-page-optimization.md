# CI 报告页面优化方案

本方案基于当前 CI 页面、保存的 CI 原始报告，以及当前社区入门、社区贡献（Issue）报告组件整理。目标是让用户快速看清：整体表现如何、哪个步骤最差、哪些问题需要优先处理、问题影响多少次执行和多少个 PR。

本次交付为页面优化方案，不修改页面或导入数据。文中的具体数值均为已保存报告的历史数据，不代表实时状态。

## 1. 当前页面的问题与改进方向

| 已核实的现状                                                     | 用户受到的影响                       | 改进方向                                                         |
| ---------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| 已显示综合分和四维度分，页脚和深度分析仍写“不打总分”             | 同页信息矛盾                         | 删除旧文案，统一为综合评分、步骤评分、维度评分                   |
| 总分卡点击后打开大段“本页怎么读”                                 | 想看得分原因，却需要先读评分理论     | 总分旁设置“评分说明”，默认只展示短说明，详细公式按需查看         |
| 痛点分散在维度详情、步骤详情、深度分析中                         | 需要多次展开才能知道先处理什么       | 概览直接显示重点问题；下方提供统一痛点列表，步骤与维度只负责筛选 |
| “主轴、家族同构、双信号、仓级回退、机理”等解释占据大量小字       | 阅读成本高，掩盖分数和事实           | 删除设计过程描述；必要术语改为易懂中文；规则移入说明             |
| 当日分析默认展示多张矩阵                                         | 数据密度高，关键问题不突出           | 矩阵收进“详细数据”，保留查询能力                                 |
| 深度分析包含固定结论，如“失败主要是平台的锅”“被卡住的 PR 在累积” | 可能与当前数据、日期或归因状态不一致 | 用明确数据和条件生成短结论，无证据时不判断责任或因果             |
| 分数和问题来自不同 JSON，缺少日期时存在各自回退到最新日的逻辑    | 可能把不同日期的信息放在同一报告中   | 仓库、日期、评分版本一致后才能组合展示；缺失内容明确显示暂无数据 |
| 当前 runtime 数据到 2026-09-10，原始报告到 2026-09-15            | 单改样式不能反映新报告               | 实施时同步核验两套数据与仓库注册，不把旧数据包装成新报告         |

## 2. 推荐页面结构

延续社区入门和社区贡献的“报告概览 → 体验步骤 → 对应痛点与证据”阅读顺序。CI 增加独立的四维评分行，但不再让多个大面板重复讲同一问题。

```text
返回 CI 看板                         仓库选择   报告日期

┌ 报告概览 ──────────────────────────────────────┐
│ 综合体验评分   本次执行次数    重点问题数    受影响 PR 数 │
│ 日期、评分可信度、评分说明                           │
│ 重点问题：优先展示 2～3 条，点击进入对应痛点详情          │
│                                                  │
│ 维度评分：稳定性 / 执行效率 / 反馈与修复 / 资源使用       │
│                                                  │
│ CI 体验步骤：步骤名 + 得分 + 痛点数                    │
│ 触发确认 → 构建准备 → 静态检查 … → 结果反馈 → 修复重试   │
│                                                  │
│ 步骤详情：左侧步骤目录 / 右侧评分、关键数据与相关痛点      │
└──────────────────────────────────────────────────┘

痛点问题   [全部步骤] [全部维度] [全部优先级] [重置筛选]
优先级 | 问题 | 所在步骤 | 受影响执行 / PR | 查看详情

▸ 详细数据：指标趋势、执行记录、阶段分析、资源消耗
▸ 评分与数据说明
```

“重点问题”是统一问题列表的摘要，不创建第二套问题状态或统计。步骤详情引用同一问题实体，展开后共用同一个详情组件。

### 报告概览：先看结果，再看风险

- 四张概览卡使用社区入门和社区贡献相同的圆角、数字样式、提示图标。综合评分显示 `/100`，重点问题数标明“紧急 / 优先处理”数量。
- 桌面端保留参考页面的左右双栏：左侧 2×2 指标卡，右侧重点问题。日期、样本和评分说明放在标题附近，避免让报告版本等元数据占据半屏。
- 首屏重点问题最多 3 条，每条只显示“优先级 + 问题短标题 + 影响”，并提供“查看全部 N 个问题”。这是展示上限，不截断底层数据。
- “受影响 PR 数”必须按完整问题关联记录去重；若只有各问题的汇总数、无法可靠去重，则改用“失败执行次数”等可验证指标，不直接求和。
- `low_confidence` 为真时，在总分旁显示“评分仅供参考”，点击说明具体原因；样本不足和评分缺失分开表达。
- 不用综合分推断是否有紧急问题。高分与 P0 可以同时出现，两项都必须可见。

### 维度评分：四个分数直接可见

| 页面名称   | 数据维度    | 默认展示         | 点击后                       |
| ---------- | ----------- | ---------------- | ---------------------------- |
| 稳定性     | stability   | 得分、相关问题数 | 查看指标明细并筛选相关痛点   |
| 执行效率   | efficiency  | 得分、相关问题数 | 查看执行耗时、按时完成情况   |
| 反馈与修复 | interaction | 得分、相关问题数 | 查看失败通知、反馈与修复情况 |
| 资源使用   | cost        | 得分、相关问题数 | 查看无效消耗和重复执行情况   |

名称调整只改变展示层，不修改评分定义。四维卡不再放英文装饰标题、引导问句和多条小字。得分解释中区分“指标实际值”和“指标得分”，例如 82.5% 是失败未告知率，18 分是对应评分，不能显示成同一种数据。

### 步骤评分：保留路径，降低每张卡的信息量

- 沿用两份社区报告的横向步骤卡、选中态、下方主从详情；顺序由数据决定。
- 每卡默认保留“步骤名称、得分 /100、痛点数”；移出英文 STEP、重复星级和三项小统计。步骤编号可保留以帮助导航。
- 默认选择包含最高优先级问题的步骤；优先级相同，按受影响 PR 数、执行次数排序；无问题时选择最低有效得分步骤。
- 无分数显示“未评估”，不能显示 0 分，也不能按正常绿色处理。
- 数据中 runtime 已有 9 个步骤，包括“系统测试”，不能继续依据“八段旅程”的旧注释写死数量。
- 原始并行关系保留简短“并行”标识，避免把并行检查画成依次执行。
- 右侧详情仅默认展开“本步骤得分、关键指标、相关痛点”。分项公式、原始阶段名和日志按需展开。
- 跨步骤问题标明所有相关步骤；未能定位的保留“未定位步骤”入口，不从总问题数中消失。

### 痛点问题：一句话看清问题，一次点击看到依据

| 信息   | 默认列表                        | 详情展开                           |
| ------ | ------------------------------- | ---------------------------------- |
| 优先级 | 紧急 P0 / 优先处理 P1 / 关注 P2 | 判定依据                           |
| 问题   | 简短事实标题                    | 原始描述                           |
| 位置   | 中文步骤名                      | 原始阶段、任务名称                 |
| 影响   | 受影响执行次数、PR 数           | 持续天数、历史累计、资源消耗       |
| 原因   | 必要时标“原因待确认”            | 已确认原因、可能原因分别展示       |
| 建议   | 可省略，避免表格过宽            | 下一步动作，有依据时展示负责团队   |
| 证据   | “查看详情”                      | 执行记录、日志摘要、可用的原始链接 |

优先级沿用 CI 原始定义，仅统一标签外观，不套用社区入门或贡献报告的严重程度判定规则。现有 `root.status` 是原因确认状态，不能直接映射为“待处理 / 已解决”；没有真实跟踪数据时不制造处理进度、负责人或确认按钮。

问题详情按“发生了什么 → 影响多少 → 原因是否确定 → 下一步做什么 → 查看证据”排序。标题目标控制在一行至两行；超长原文保存在详情中，不用另一段概括性长文替代。

## 3. 删除、改写、折叠哪些内容

| 原内容或表达                           | 处理方式             | 推荐表达                                                 |
| -------------------------------------- | -------------------- | -------------------------------------------------------- |
| “本页不打总分”“改进效果……不打总分”     | 删除                 | 页脚只保留产品、报告名称、数据日期                       |
| “主轴=旅程段（仓无关，家族同构形态）”  | 删除                 | 模块名用“CI 体验步骤”                                    |
| “两条通道，互不改写”“慢性水平”“翻译官” | 移出正文并改写       | “评分反映整体表现，问题优先级表示处理紧迫程度。”         |
| “段三宫格”“事件 + 水位双信号”          | 删除                 | 直接显示执行次数、痛点数等具体标签                       |
| “仓级回退格”“无日度信号”               | 改写                 | “该步骤暂无此项数据”                                     |
| “当日分析 · 下钻明细”                  | 改名并默认折叠       | “详细数据”                                               |
| “机理”“责任方”                         | 按语境改写           | “失败原因”“负责团队 / 原因待确认”                        |
| run / workflow / TTFF                  | 普通界面中文化       | “执行”“流水线”“首次失败反馈时间”                         |
| PR 转绿时长                            | 改写，保留口径提示   | “PR 恢复通过耗时”                                        |
| Flaky 率（近似）                       | 改写，不删除近似性质 | “疑似偶发失败率”                                         |
| 机时                                   | 加单位解释           | “机器使用时长（小时）”，说明为累计占用时长               |
| “失败主要是平台的锅，不是贡献者代码”   | 删除固定结论         | 有证据才写“已确认平台故障影响 X 次执行”                  |
| “被卡住的 PR 在累积”                   | 按实际方向生成       | “受影响 PR 从 X 个增加至 Y 个”；下降则写减少             |
| “回填台账”“治理健康度”“集中度守卫升格” | 移到规则或详细记录   | 用户侧分别展示“待确认原因”“待确认问题数”“优先级判定依据” |
| “点击展开”“再次点击收起”等重复提示     | 删除正文提示         | 按钮名、箭头与展开状态即可表达                           |

以下信息不能当作“无用小字”删除：数据日期、统计范围、指标单位、评分仅供参考、示例数据标记、缺失数据原因。将其放到清晰且固定的位置；公式、权重和技术证据则使用可点击说明，不仅依赖鼠标悬停。

## 4. 基于原始数据的展示示例

来源：`rawdata/CI 度量与改进(日观测板 _ 周复盘)_files/saved_resource.html` 内嵌压缩数据，runtime，2026-09-15。

| 项目         | 已核实数据                                          |
| ------------ | --------------------------------------------------- |
| 综合体验评分 | 82 / 100；原数据标记评分可信度较低                  |
| 四维评分     | 稳定性 95、执行效率 91、反馈与修复 60、资源使用 82  |
| 执行次数     | 当日 105 次；评分字段 `n_runs` 为 103，两者不应混用 |
| 重点问题     | 4 个：P0 1 个、P1 3 个                              |
| 较低步骤得分 | 静态检查 46、结果反馈 48、触发确认 50               |
| 无评分步骤   | 系统测试：未评估                                    |

首屏可以直接表达：“反馈与修复得分最低，为 60 分；当前有 1 个紧急问题、3 个优先处理问题。”这句话只陈述分数与问题，不推断根因。

重点问题示例：

> **紧急 P0 ｜自托管执行机上的任务失败，原因待确认**  
> 影响 34 次执行、24 个 PR。  
> 查看受影响步骤和执行记录。

其他问题包括镜像/编排（3 次执行、2 个 PR）、NPU 设备打开失败（1 次执行、1 个 PR）、失败告知覆盖率下降。最后一项的影响计数字段为 0，不能据此写“没有影响”；应展示其指标异常，若没有可确认影响范围则写“影响范围待确认”。

上述问题可能影响相同 PR，不能把 24、2、1 直接相加生成报告总影响。亦不能因为存在执行机相关问题，就将所有失败判为平台责任。

## 5. 得分和数据口径约束

| 内容         | 数据来源                                        | 约束                                                       |
| ------------ | ----------------------------------------------- | ---------------------------------------------------------- |
| 总分         | `scores.total`                                  | 直接使用报告值，不在页面用步骤分重算                       |
| 维度分       | `scores.dims[key].score`                        | 对应原始四维，不把缺失值当 0                               |
| 步骤分       | `journey[].segscore` / 当前 `stages[].segscore` | 独立用于定位薄弱步骤，不相加得出总分                       |
| 步骤内维度分 | `cells[key].score`                              | `fallback=true` 的仓库级占位数据不能展示为该步骤的真实分数 |
| 痛点         | 当日 `problems`，关联步骤信息                   | 统一实体去重，多步骤展示同一问题不重复计入报告总数         |
| 原始指标     | `metrics`、`dims[].vals`、`meta`                | 保留单位、分母、滚动周期及示例标记                         |
| 历史趋势     | 同仓库各日报告                                  | 评分版本和口径一致才直接比较；缺失日期留空，不补零         |

用户侧评分说明默认只写两句：“综合评分由四个维度计算。步骤评分用于定位薄弱环节，不与综合评分相加。”具体权重、缺项处理、P 级对步骤分的限制，放入该版本的详细评分规则。

当前页面以日为选择单位，第一阶段继续按日展示，不把固定周数据跟随日期选择包装为当日分析。周报告若后续开放，需独立提供准确周期、完整数据和周聚合口径，不能把当前日分称为周分。

数据更新时同时检查：原始报告有 19 个仓库，而当前 `CiRepoKey` 类型列出 17 个；应核实新增仓库是否需要开放，并同步注册、选择器和 JSON，不能仅依赖文件生成成功。

## 6. 与社区报告保持一致的视觉和交互

- 复用社区入门 `ReportSummaryCard`、`JourneyPanoramaSection` 的概览与步骤组织方式；参考社区贡献 `IssueReportOverview`、`IssueExperiencePath` 的左右布局、步骤目录和痛点呈现。
- 延用浅蓝灰背景、白色主卡、主卡 24px 圆角、内部卡 16px 圆角、浅色边框和轻阴影；外部间距约 20px，主卡内边距约 24px。
- 主标题约 16 ～ 20px，正文和表格主要信息 14px，辅助信息 12px；避免当前大量 10 ～ 11.5px 文字承载关键结论。
- 数字统一字体和对齐方式。综合分、步骤分及维度分均使用 `/100`；不再同时用星级、等级字母、分数表达同一结果。
- 蓝色用于选择与链接，红色标紧急问题，琥珀色标关注项，灰色标未评估；不能仅靠颜色区别状态。
- 保留同款评分说明图标、展开箭头、空状态、表格分页。CI 不另建一套视觉语言，也不直接嵌入原始 HTML。
- 小屏概览转为两列或单列；步骤卡横向滚动，问题详情占满宽度；不能靠缩小字体挤下全部内容。
- 步骤选择、维度选择、重点问题跳转共用筛选状态；显示当前筛选及结果数，提供重置。切换仓库或日期时清理失效选择。

## 7. 实施范围和顺序

| 顺序          | 涉及文件 / 模块                                                                      | 具体工作                                                                             |
| ------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| 1. 数据核对   | `update_ci_data.py`、`types.ts`、`data.tsx`、`journeyData.tsx`                       | 核对原始数据导出、仓库注册、评分版本、字段缺失、日期一致性；更新过时的来源和八段注释 |
| 2. 首屏重构   | `CiReportOverview.tsx`、`CiExperience/index.tsx`                                     | 概览指标、重点问题摘要、四维评分、精简页脚；移除总分卡长文入口                       |
| 3. 步骤与痛点 | `CiJourneyPanorama.tsx`、`ProblemPanel.tsx`、`ProblemCard.tsx`、`CiReport/index.tsx` | 精简步骤卡、统一问题实体和详情组件、增加统一问题表、打通筛选与定位                   |
| 4. 收拢明细   | `DailyDrilldown.tsx`、`DeepAnalysis.tsx`、`Appendix.tsx`                             | 矩阵折叠、用条件化事实摘要取代固定结论、集中评分与数据说明                           |
| 5. 样式与验收 | 复用或抽取社区报告展示组件                                                           | 统一视觉、响应式与交互；不共用不同报告的评分业务规则                                 |

优先完成数据核对、首屏与痛点可见性，再补齐趋势和高级分析。现有 `ScoreCards.tsx` 并未在当前 `CiReport/index.tsx` 主渲染链路使用，应基于实际入口修改，避免只改到旧组件。

## 8. 验收标准

- 无需展开任何说明，即可看到总分、四维分、重点问题；继续浏览即可看到所有步骤分。
- 任一问题至多一次点击即可查看完整影响、原因状态、建议和执行证据。
- runtime 2026-09-15 示例准确显示总分 82、四维 95/91/60/82、4 个重点问题；系统测试显示未评估。
- 总分高且存在 P0、无问题但分数低、无数据、评分不可信、跨步骤问题均有独立且正确的呈现。
- 当前日期缺少得分或问题数据时，不静默混入其他日期；没有同口径比较数据时不生成上升或下降结论。
- 不重复累计跨步骤问题、PR 或执行次数；关键指标有明确统计范围。
