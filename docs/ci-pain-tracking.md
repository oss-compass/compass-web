# CI 痛点管理：方案与实现

## 范围

保留原 CI 页面优化方案，本次只增加痛点人工判断和修复跟踪。参考原 HTML“校准确认”的证据优先、无法判断不猜测、判读人及时间留痕，以及 Issue 痛点管理的状态标签、步骤条、判定弹窗和操作记录。

原 HTML 的校准是 Flaky 抽检和目标线确认，浏览器保存后导出。本次面向报告中的每个痛点，不照搬抽检题目，不调整分类器和评分，不细分“无需修复 / 必须修复”，也不逐个 PR 判断。

## 状态和动作

| 当前状态           | 可操作                        | 操作结果                       |
| ------------------ | ----------------------------- | ------------------------------ |
| 待确认             | 确认有效问题 / 判为非有效问题 | 有效问题、待修复 / 非有效问题  |
| 有效问题、待修复   | 完成修复                      | 已完成修复、待复测             |
| 已完成修复、待复测 | 撤销修复                      | 有效问题、待修复               |
| 非有效问题         | 改判为有效问题                | 有效问题、待修复，需要重新修复 |
| 有效或已修复       | 判为非有效问题                | 非有效问题，原修复状态失效     |
| 非待确认状态       | 回退待确认                    | 待确认，重新判读               |

所有操作要求提交人；确认有效或改判有效不填写依据，只有判为非有效问题必须填写判断依据；修复、撤销、回退的说明选填。保存操作前后状态及服务端时间。不自动把报告里的归因状态、根因已核或分数解释为有效性确认；未确认、非有效问题不能直接完成修复。

仅“已修复待复测”状态显示重跑及重跑记录入口，按钮禁用并显示“暂未开放”。“已完成修复”只是人工声明，不能显示复测通过或已闭环；没有重跑任务接口、调用、轮询或模拟结果。

## 页面

- 报告概览和步骤详情的每个痛点右侧使用状态按钮作为管理入口，与 Issue 报告共用胶囊按钮；不再分开显示状态标签和“痛点管理”按钮。展开详情箭头为独立按钮。
- 步骤全景图下增加 CI 痛点管理表，支持全部、待确认、待修复、已修复待复测、非有效问题筛选及计数。
- 同一痛点的多个入口使用一个报告级状态源；修改后立即同步。
- 弹窗展示问题描述、当前处理区、影响、原始归因、原因与推测、证据、完整分页执行记录和 PR 链接。
- 待确认、已确认待修复、已修复待复测、非有效问题使用统一状态卡片：顶部展示阶段、说明和状态标签，下方固定为提交人及当前状态可执行操作。保存时禁止关闭和重复提交，失败保留输入。
- 待确认使用两张大选项卡直接选择“是，有效问题”或“否，非有效问题”；确认有效直接进入待修复，判为无效时再打开依据弹窗。
- 已确认待修复默认展示修复说明和“完成修复”，不再先选择动作再展开表单；已修复待复测才展示重跑占位和撤销修复；非有效问题展示恢复入口。
- 加载失败显示错误和重试，不将失败当作“全部待确认”；冲突时重新加载并要求重新操作。
- 切换仓库或日期销毁旧弹窗，取消旧读取，避免旧请求写入新报告界面。
- 弹窗与 Issue 报告一致：最大宽度 1280px、70vh 滚动内容、顶部带时间的状态步骤条、浅红问题摘要、统一圆角状态操作卡、可折叠操作记录。展示状态统一为“待确认 / 已确认待修复 / 已修复待复测 / 非有效问题”；重跑仍不开放。

## 身份与存储

独立 ES 索引 `ci_pain_trackings`，可通过 `ES_CI_PAIN_TRACKING_INDEX` 配置。跟随后端启动初始化，不将业务状态存到 localStorage；localStorage 只复用 Issue 的提交人记忆。

跟踪范围：组织 + 仓库 key + 流水线 + 报告日期。问题身份：维度 key + kb + 完整问题标题；不包含步骤，同一痛点跨步骤只管理一次。后端使用范围和问题身份的 SHA-256 作为文档 ID。

本期不进行跨日报告的模糊匹配或自动继承，避免某次修复覆盖后续复现。相同报告、相同身份刷新或换浏览器可继续管理；标题或维度改变按新问题待确认处理，历史记录仍保留在存储中。后续若引入上游稳定 pain_id，再设计跨日报告续接与复现。

使用 revision 和 ES seq_no / primary_term 乐观锁，首次创建使用 create，拒绝覆盖并发操作。不修改原始 JSON、原始报告、分数或问题数量定义；管理表的状态计数与报告检测问题数分别呈现。

## API

前缀沿用部署配置：默认 `/user-journey-api/user-journey/ci-experience`；前端复用 `NEXT_PUBLIC_COMPASS_API_URL` 和 `NEXT_PUBLIC_USER_JOURNEY_API_PREFIX`。

- `GET /pain-trackings?org=cann&repo=runtime&workflow=runtime_action&day=2026-09-15`：返回 `{items}`，仅已人工操作的问题有记录，其他默认为待确认。
- `POST /pain-trackings/actions`：请求包含上述四个 scope 字段，以及 `problemKey`、`type`、`operator`、`revision`；`reason` 仅判无效时必填，其他操作可省略。返回 `{message,data}`。
- action：`confirm / mark_invalid / restore_valid / mark_fixed / undo_fixed / reset`。
- 非法状态或旧版本返回 409；业务输入错误 400；参数校验错误 422。重跑不是允许的 action。
- 响应记录：`problemKey,status,revision,updatedAt,history[]`，history 保存 `action,from,to,operator,reason,at`。

接口访问方式与当前 Issue 人工确认接口一致，为公开读写、提交人署名。提交人是人工填写的操作记录，不是经过认证的账号；不引入或暴露管理员令牌。CI 报告当前来自前端静态文件，因此本期不做服务端报告存在性校验；管理记录与评分系统隔离。

## 部署与验收

先部署后端（启动创建新索引）再部署前端，不需改已有报告或迁移 Issue 状态。开发过程不写生产 ES、不重启生产服务。

验证有效确认 → 修复 → 撤销、无效 → 改判、回退重判、审计记录、数据持久化、并发冲突、范围隔离、API 参数和重跑拒绝；前端验证入口共享状态、必填校验、保存失败及占位按钮。
